# Coffee Terminal：项目介绍与 UI 设计交接

资料日期：2026-09-19。功能基线：`feat/digital-twin` 分支 `8397640`。本包描述该分支当前能力，不能视为 main 已发布能力。用途是交给专业 UI 设计软件分析、重新组织信息与改善交互，不是新产品需求或最终设计稿。

- [UI-SPEC.md](UI-SPEC.md)：现有页面区域、响应式规则、状态语义、改进问题与验收要求。
- [device-lab.html](device-lab.html)：虚拟设备联调台的当前布局范例。
- [digital-twin.html](digital-twin.html)：工作台仿真实验室的当前布局范例。
- [联调台桌面截图](assets/device-lab-desktop.png) · [实验室桌面截图](assets/digital-twin-desktop.png) · [联调台窄屏](assets/device-lab-mobile.png) · [实验室窄屏](assets/digital-twin-mobile.png)：供不执行 HTML/JavaScript 的工具使用。

HTML 保留业务页面 DOM 与 CSS 的布局结构，使用演示脚本填充数据。顶部“设计参考”条是本包添加的说明，**不是产品现有导航**。三维区域为本项目真实场景截图，不能旋转、控制设备或代表新的三维仿真。演示操作不调用 API、不写服务配置；刷新恢复样例。状态选择器、设备选择、四个标签、保存反馈、命令示例、开始/暂停与回放滑块可供设计观察；其余操作仅显示“演示”提示。不要把这些局部演示当作完整功能验证。

## 项目是什么

Coffee Terminal Simulator 是自动咖啡工作站的软件联调环境。原有 Python/pywebview 桌面模拟器用于验证云端订单、制作流程、库存、告警与异常恢复；本分支在此之外提供三维数字孪生、独立虚拟设备接口与仿真实验工具。

核心目标：在没有真实机器的情况下，让工程师调试“命令发给谁、何时执行、如何读取状态、失败后怎样恢复”，并观察设备布局和双臂流程。不是消费者点单应用，也不是工业安全认证或真实机器人控制系统。

## 用户与工作目标

| 用户 | 主要任务 | 最需要看到的信息 |
|---|---|---|
| 设备/接口工程师 | 调整单设备参数，发送动作，检查状态与结果 | 当前设备、连接/故障状态、命令 ID、反馈、传感器 |
| 规划软件工程师 | 调用设备接口，协调双臂与设备，检查失败恢复 | 任务依赖、设备占用、执行/通知区别、最终结果 |
| 仿真/布局调试人员 | 设置安装坐标，验证流程和路径 | 坐标单位、父安装点、世界位置、碰撞提示 |
| 演示/项目人员 | 看懂完整制饮和策略差异 | 场景、当前阶段、完成度、耗时、结论 |

## 产品组成与关系

| 页面/子系统 | 当前作用 | 与其他入口的关系 |
|---|---|---|
| 原终端 `index.html` | 扫码提示、制作进度、取杯、异常/恢复核验；开发控制台 | 连接独立 Coffee Cloud 项目；计时执行业务任务 |
| 原展示页 `robot-scene.html` | 三维制作演示、关节和时间轴调试 | 展示用途；不等同虚拟设备接口服务 |
| 虚拟设备联调台 `device-lab.html` | 配置布局/设备，发单条命令，看状态、故障、库存、运行一键联调场景 | UI 与外部规划软件使用同一独立设备服务 |
| 仿真实验室 `digital-twin.html` | 本地 Worker 运行任务图，比较串并行、观察时间线、导出与回放 | 从联调台**复制配置快照**，不共享运行状态 |

本包的 HTML 重现后两个页面。原终端和展示页提供背景说明，未制作其离线交互范例；云端手机点单、支付、后台管理不属于本包改版范围。

**关键关系**：联调台保存配置 → 实验室载入配置并重置 → 实验室独立运行。联调台后续修改不会自动覆盖正在运行的实验；载入也不会操控联调台的现场设备。两边的时钟、当前持杯、实际库存、命令与故障彼此独立。

## 当前功能

### 虚拟设备联调台

- 11 个设备入口：左右机械臂、左右夹爪、落杯器、咖啡机、奶泡机、热水机、制冰机、糖浆机、封盖机。
- 单条命令：动作、参数、命令 ID、最迟启动等待；查询、取消、复位；同 ID 重发不重复执行。
- 三种时钟：实时、加速、手动；视角切换、设备定位、碰撞代理显示、杯槽状态和取杯。
- 单设备配置：执行时间、通信延迟、库存/物料、运动限制及完整 JSON。部分参数通过专用字段编辑，复杂参数仍依赖 JSON。
- 安装配置：父安装点、位置（mm）、XYZ 旋转（°）、原点显示与默认安装恢复；工具随所属机械臂法兰运动。**尚不能用鼠标在模型表面选安装点**。
- 独立夹爪：最大仿真开口 120 mm，开合速度可设；抓取/释放体现开合过程，状态包含开口、运动和持物相关信息。120 mm 是仿真扩展，不是硬件实测规格。
- 落杯检测：杯垫检测是否有杯，支持检测范围、容差与报告延迟；强制传感器值只改变报告，不生成杯子。
- 异常模拟：设备故障、断连/重连、丢确认、丢完成通知、传感器异常。
- 四种一键场景：正常制饮、卡杯、加工中断连、丢通知后查询恢复。正常场景包含 32 个接口任务。
- 补料、导出配置、导入配置并重置、重置整个实验；重置会创建新会话，清空当前动作/故障/成品并恢复初始库存。

### 仿真实验室

- 内置任务图制饮、串行/双臂并行策略；开始/暂停、单步、重置、1×/4×/16×速度。
- 设备与物料状态、容器持有关系、任务甘特时间线、事件日志、策略比较。
- 共享配置来源与快照提示；导入场景/联调配置、导出实验、导入轨迹回放、滑块定位。
- 设备故障、维修复位、牛奶补料；这些是实验本地操作，不模拟设备 API 的全部通信异常。
- 有关节限制、逆运动学、简化碰撞查询、动作依赖、资源占用及质量账本。落杯、出液、封盖、夹爪、倾奶都有状态驱动的表现。
- main 布局倾奶为倾杯—出液—回正；夹爪在杯子附近沿手指方向接近/退出。不能据此保证任意自定义布局都无穿模。

## 必须保留的边界

没有通用拖拽流程编排器；没有真实串口/RS485/Modbus 驱动；没有流体求解或精细刚体接触；并非所有显示模型都有精细碰撞体。不能把“状态可配置”设计成已接入真实硬件，也不能把“完整示例流程”设计成已支持任意配方编排。

设备服务主要状态属于当前进程/会话。用户应能理解刷新页面、设备复位、重置实验、导入并重置、服务重启的差别。真实配置导出可能包含自定义参数，不应在设计演示中混入用户服务快照或凭据；本包采用仓库默认配置与构造的样例数据。

## 品牌依据

品牌层级：**Coffee Terminal 为主品牌；BY QARM / 千臂机器人是次级背书**。当前联调台已经采用 v1.1 品牌令牌，实验室保留较早样式，存在统一空间。不要把现有实验室的每个颜色都当成品牌规范。

- 奶油背景 `#F6F0E5`、浅表面 `#FFF9F0`、边线 `#DDD3C4`。
- 主标题 `#17382D`、正文 `#342F2A`、次级文字 `#746D64`。
- 森林绿 `#1F5A46` / `#34795D` 用于主操作和品牌层级；黄铜 `#B78A52` 用于少量强调；技术日志底色 `#0D1713`。
- UI 采用系统无衬线字体栈；品牌展示标题可用宋体/衬线；数字、ID、日志使用等宽字体。HTML 不从网络下载字体，实际字形由平台字体决定。
- 状态必须配文字/图标，不能仅靠颜色。品牌规范中的展示动效不是每个工程页面必须套用的功能。

## 可以直接给设计工具的需求

> 请阅读 README.md 和 UI-SPEC.md，并打开两个 HTML 范例及品牌规范。先分析现有的信息架构、关键操作可发现性、状态反馈和密集表单问题，再提出桌面优先、移动可查看的改进稿。请保持 Coffee Terminal 主品牌和 QARM 次级背书。优先打通“选设备—发命令—观察—查询结果”和“保存配置—载入实验—运行—分析”两条路径。区分当前已实现功能与提议新增能力；不要虚构真实硬件接入、任意流程编排或实时共享运行状态。输出页面结构、组件/状态规范、桌面与窄屏稿、改动优先级及验收方式；不要只给一张美化后的首页。

建议交付：现状问题列表（按影响分级）、页面线框、两个主要页面高保真稿、组件状态表、响应式说明、空/加载/断连/失败/过期/成功样例、可供前端实现的标注。每个建议应说明解决哪个用户任务，新增功能应独立标记。
