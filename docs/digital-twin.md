# 咖啡工作台数字孪生：运行、架构与标定说明

本次增加一个可运行、可重复实验的独立仿真入口。它采用 Three.js 展示、Rapier 几何碰撞查询、固定步长内核、双臂任务图以及设备／物料模型。浏览器 Web Worker 和 Node 命令行使用同一份内核。原来的生产进度展示入口继续保留，可用于视觉参考。

这是一套**运动学与工艺时序仿真平台首版**。完整示例可以运行，但默认机械尺寸、夹具、速度、设备时间和耗材数量尚未经过实机标定。示例运行成功不代表任何真实工作站已经获得验证。

## 1. macOS 快速运行

准备 Node.js 22 或更新版本，以及 Python 3。进入 `coffee-terminal-simulator` 仓库后运行：

```bash
npm ci
npm run start:twin
```

打开 `http://127.0.0.1:9120/digital-twin.html`。启动脚本只监听本机回环地址，提供公开网页资源。无需云端、数据库、ROS、V-REP、Webots 或 GPU 计算平台。构建后 Three.js 与 Rapier WASM 都随本地资源提供，不依赖运行时 CDN。

若只想构建或换端口：

```bash
npm run build:twin
python3 scripts/serve_scene.py --twin --port 9130
```

macOS 启动方式沿用仓库既有 Python 服务。2026-09-17 集成时已在 macOS、Node.js 24.20.0 上执行本节启动命令，并用 Playwright 驱动 Chromium 151 验证页面；Safari 和实体移动设备尚未验证。

## 2. 如何操作

1. 默认显示与原展示入口共用资源的品牌门店；可切换「门店全景／工作台／俯视」，勾选「工位」显示标签，勾选「碰撞几何」查看实际参与检测的简化几何体。点击「开始」运行完整制饮流程。「暂停」「单步」「重置」控制仿真；速度只改变墙钟推进速率，不改变内核时间步。
2. 左臂取杯、移动至咖啡机、释放杯子后萃取；右侧同时制备牛奶。设备加工期间不会一直占用机械臂。
3. 左臂将咖啡杯放到交接台并撤离。右臂携带奶容器到倒奶位置，执行有耗时的物料转移，再放回奶容器，取走咖啡杯送至封盖机。放杯并退让后封盖，再夹取送往成品取杯台。
4. 观察设备预热／运行／清洁恢复／故障状态、剩余物料、预留量、容器内容物、任务时间线和事件。
5. 点击「比较两种策略」，在同一配置下分别运行串行和并行调度。比较的是任务调度，不是自动生成最优路径或全局最优排程。
6. 设备运行期间注入故障：已流出的物料保留，未使用的预留量释放，当前任务失败，下游依赖任务跳过。维修恢复设备可用性，**不会自动重试失败配方**，避免重复投料。要重新制作，重置实验或提供新的任务图。
7. 缺料会让任务等待；补料后可继续。容器容量不足会在投料前失败。
8. 「导出实验」保存场景、任务图、命令、事件、状态轨迹、最终状态与指标；「导入实验回放」通过滑块浏览已记录状态。回放期间禁止故障和补料命令。

## 3. 不打开页面也能做实验

```bash
# 一次完整制饮
npm run twin:run

# 串行／并行比较
npm run twin:run -- --compare

# 保存单次实验（含每 10 个时间步的状态快照）
npm run twin:run -- --output /tmp/coffee-experiment.json

# 按记录的场景、任务、命令重新计算，并严格比较最终状态
npm run twin:run -- --replay /tmp/coffee-experiment.json

# 使用自己的布局和任务图
npm run twin:run -- --world /path/to/world.json --tasks /path/to/tasks.json --max-seconds 600
```

达到时间上限仍未完成时，命令退出码为 1，输出等待原因；不会将等待中的任务认定为成功。`--compare --output` 导出的是含 `experiments` 数组的比较文件；页面回放和 `--replay` 使用其中单个实验对象，或直接导出单次实验。

当前默认配置为完整 main 布局 `coffee-workcell-main-v2.json`，包含全部台面设备、直立搬运、底座绕行和封盖。旧版简化场景 `coffee-workcell-v1.json` 仍可显式加载，原 92.32 / 70.92 s 属于旧布局。当前保守路径和运动限制下：

| 策略 | 完成任务 | 仿真完工时间 | 最终杯中物料 |
|---|---:|---:|---:|
| 串行 | 31 / 31 | 318.30 s | 0.220 kg |
| 并行 | 31 / 31 | 265.62 s | 0.220 kg |

两者都消耗咖啡豆 0.018 kg、水 0.040 kg、牛奶 0.180 kg。模型将 0.018 kg 咖啡豆质量记入废料，杯中得到 0.040 kg 咖啡产物和 0.180 kg 牛奶。该简化质量模型不模拟萃取溶出比例。上述约 16.6% 的时间差仅用于验证调度机制，不能作为真实设备收益承诺。

| `coffee-terminal/web/twin/collision.mjs` | Rapier 形状距离／接触查询、持物位姿同步、碰撞过滤 |
| `coffee-terminal/web/twin/planner.mjs` | 直达、接近、撤离、抬高等候选路径与逐段验证 |
| `coffee-terminal/web/twin/kernel.mjs` | WorldState、仿真时钟、资源锁、设备、物料守恒、事件、实验导出 |
| `coffee-terminal/web/twin/recipes.mjs` | 默认 31 节点拿铁与封盖任务；旧配置保留 25 节点 |
| `coffee-terminal/web/twin/renderer.mjs` | 只读状态的 Three.js 渲染器、共用门店、灯光、视角与 GLB 外观加载 |
| `coffee-terminal/web/twin/visuals.mjs` / `visual-state.mjs` | 复用旧场景柜体与品牌杯具；坐标、关节位姿和物料到外观的只读适配 |
| `coffee-terminal/web/twin/worker.mjs` | 浏览器中唯一的仿真状态写入者 |

| `scripts/run_twin.mjs` | 批量运行、比较、确定性重算入口 |

原 `web/robot/` 代码没有被复制为第二套生产执行器，也没有把动画时长继续当作加工时长。新入口允许独立调整世界和配方；本次未接入云端生产订单或真实机械臂控制器。

## 5. 坐标、场景与模型标准

- 内核：右手系，Z 向上；单位为米、弧度、秒、千克。
- 位姿：`{"position":[x,y,z],"quaternion":[x,y,z,w]}`，四元数必须归一化。
- 世界中的机器人底座、工位和静态设备使用世界位姿；机器人链和工具使用局部位姿。
- 渲染器根节点绕 X 轴旋转 -90°，把内核 Z-up 映射到 Three.js Y-up。不要在各模块零散交换 y/z。
- 固定步长默认 0.02 s。内核使用整数 tick 累计时间；页面帧率、拖动视角、播放倍率均不改变物理／工艺时间。
- 每个实体使用稳定 id。修改布局后同步修改相关工位的位姿；当前还没有父子坐标系编辑器或自动标定工具。
- 构建会把 `config/twin/` 中的 main-v2 和旧版 v1 配置复制到网页目录，请编辑源配置，不要手工维护两份。

### 无须建模也能修改设备

碰撞模型中，设备外壳是带尺寸的长方体，容器是圆柱，机械臂连杆是胶囊；外观独立采用品牌门店、精细柜体和杯具模型。先用尺子测量设备外壳和关键作业空间，就能替换 JSON 的 `size`、`pose`、`stations`。碰撞外壳目前是每项一个长方体；同一设备需要复杂包络时添加多个障碍物，给取杯口留出实际空间。

默认 main 布局共用完整 `createWorkcell()` 外观；改动工位或碰撞体后切回参数化外观，避免继续显示位置已不相符的固定模型。自定义布局可以换成本地 GLB。把文件放到 `coffee-terminal/web/assets/twin/`，在对应障碍物添加：

```json
"visual": {"url":"assets/twin/coffee-machine.glb", "scale":1}
```

外观模型坐标采用 glTF Y-up，加载时统一转为局部 Z-up；原点应放在设备配置中心。外观加载不会改变碰撞几何。普通设备外壳可用免费素材或 AI 模型，机器人关节轴、TCP、夹具接触面和设备开口尺寸必须有尺寸依据。GLB 只允许同源资源，加载失败时保留参数化外壳。

机器人外观使用银色连杆、蓝色关节端盖与夹具细节，所有关节、连杆和 TCP 位姿仍直接来自仿真 FK；没有调用旧展示场景的动画 IK 或时间线。URDF 导入记录 mesh URI，但当前不会自动解析 `package://`、下载厂家 mesh 或把全部 mesh 转为凸碰撞体。这样可以先使用厂家运动学描述，后续独立提高外观细节。选资产时自行核对具体资产授权。

## 6. 接入真实机器人描述

默认是 UR10e 标称 DH，尚未输入工厂标定偏差。每个轴都独立配置 `min/max/velocity/acceleration/jerk`。默认限制是仿真实验值，不是对真实 UR10e 极限的声明。

如果厂家提供展开后的 URDF：

```bash
python3 scripts/import_twin_urdf.py /path/to/robot.urdf \
  --robot left --base base_link --tip tool0 \
  --output /tmp/real-robot-world.json
npm run twin:run -- --world /tmp/real-robot-world.json
```

导入器接受六个独立旋转关节及中间固定关节，保留 origin、axis、关节位置限制与速度限制。xacro 须先由厂商工具展开；移动关节、闭链、mimic 不支持。加速度／jerk 从模板保留，须人工填写厂家或控制器实测值。连续关节暂采用 ±2π 的有限范围。

**必须检查 `tool`：** URDF 的 tip 若已经包含夹具 TCP，应把附加工具变换设为单位变换，避免重复叠加工具长度。还需替换 `base`、`home`、碰撞半径和允许接触对。导入成功仅表明配置可解析，不等于原来的工位与路径适合新机器人。

现有 IK 是有多个初值的阻尼数值法。轨迹为每段起止速度、加速度为零的五次关节插值，解析限制最大速度、加速度与 jerk；不是厂家控制器轨迹，也不是 Ruckig。各段的 jerk 可以跳变，未约束 snap。后续替换 Pinocchio／其他 IK 或 OMPL／Ruckig 时，保留 `fk/ik/trajectory`、规划结果和 WorldState 边界即可。

## 7. 碰撞、抓取与运动的准确含义

Rapier 在此版本用于形状几何查询，**没有执行刚体重力、接触力或关节动力学积分**。因此本版本能研究无碰撞运动的工艺时序，不能预测打滑、掉杯、夹持力、力矩、柔性、振动或碰撞后的反弹。

- 检查机械臂自身、双臂之间、设备、容器，以及随夹具移动的容器。
- 胶囊包络半径和静态箱体来自配置，默认间隙阈值为 2 mm。
- 固定底座与桌面安装接触由 `allowedCollisionPairs` 精确列举。
- `allowedSelfPairs` 显式配置相邻连杆接触例外；换机器人后必须复核这些例外与几何近似。
- 夹爪末端与目标容器只在指定接近／抓取／撤离任务以及持物期间允许接触；其他连杆不能因此穿杯。
- 抓取必须在目标 12 mm 内且物体无归属；成功后固定相对变换。放置必须在工位 15 mm 内。默认示例是一个抽象夹具，不是已验证的真实手指形状。
- 每个候选轨迹按仿真步长采样，并按关节变化量加密检查。双臂同时运动时仍逐 tick 校验组合姿态，碰撞停机时不提交候选状态，也不推进本 tick 物料。
- 这不是旋转刚体的严格连续碰撞检测证明；非常薄的障碍或高速运动仍可能在采样之间漏检。降低 dt、加大几何余量、采用保守连续包络是后续高精度工作的方向。
- `stop` 模式遇碰撞停止；`shadow` 模式在运行时记录碰撞并继续。运动规划器在两种模式中都拒绝已检出的碰撞路径，shadow 不是强制穿透规划器。
- 候选路径穷尽时明确报 `NO_SAFE_ROUTE`。不存在路线时不瞬移、不强行沿目标动画走。与另一个运动中的机械臂冲突会停机，目前没有自动多机器人联合重规划。

倒奶是容器间的定时质量转移，校验两个容器接近、目标容量、源容器归属；当前不求解倾倒姿态／重力出流，也不模拟泡沫膨胀或液面。未来可将倾倒动作拆成姿态轨迹与定时出流动作，不必引入 CFD。

## 8. 设备、物料与任务图

设备状态为 `warming → idle → running → cooldown → idle`，故障切换至 `fault`。当前清洁恢复用配置秒数表达，不另耗水；热水机包含同一套接口，默认拿铁示例不调用热水任务。

每个工艺动作启动时检查完整所需库存并预留；每 tick 实际扣除源物料、增加目标容器质量，差额计入废料。中途中断不撤销已经发生的转移。初始库存、补料、剩余量、消耗量与所有容器／废料可做质量守恒核对。容量以质量近似，没有根据温度／密度换算体积。

任务字段示例：

```json
{
  "id":"extract",
  "type":"process",
  "after":["left-retreat"],
  "resources":[],
  "device":"brewer",
  "object":"cup"
}
```

支持 `move/grasp/release/process/transfer/wait`。机器人、设备、物体资源由内核补齐；额外共享区域可在 `resources` 中使用 `zone:handoff` 等名称。调度按配置顺序遍历就绪任务，一次性申请所需锁，没有占住部分锁继续等待的行为。物体持有关系跨任务保存；设备加工不自动占用机器人。DAG 在启动前检测循环和失效引用。

单杯默认示例验证双臂配合。多杯订单、库存补给／清洁人员、排队区和最优排程求解器仍需显式建模，不能从单杯时间简单推断连续门店吞吐量。
